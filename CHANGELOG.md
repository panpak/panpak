# Changelog

## Unreleased

- **Step 9, PR 8: the SBOM.** Before: a package said what it was made from only in `[provenance]` (a build) or `[origin]` (a conversion), and nothing listed the libraries that a tree carries, so a person or a scanner had to unpack the package to know. Now `panpak pack` writes `.panpak/sbom.cdx.json`, a CycloneDX 1.6 JSON document, as a file of the tree (the signed index covers it), and the manifest signs its BLAKE3 hash and says how much it covers: `[sbom] hash` and `coverage` (`build` for a package made by `panpak build`, with the source, the build image and the dependencies taken from the image; `best-effort` for the rest, with the libraries of the tree, each with its SONAME, path and BLAKE3 hash, and for a conversion the file it was made from). The table is not critical (§3.1.12) and `pack` refuses one in `panpak.toml`. The document is deterministic (no time, no serial number, no name of the app, fixed order): the tree of a package is addressed by its content, so a name in the file would make the same files under two names two trees. `panpak sbom <package | app id | URL>` shows it: from a package or an installed app it checks the file against the signed hash, and from a URL it reads the footer, the manifest, the signature, the index and only the chunks of the SBOM by range requests (4.5 MB package: 2,930 bytes downloaded in `tests/sbom.py`); `panpak sbom --export` writes the complete document for a scanner (the name, id and version from the signed manifest, a serial number that is the same for the same package, and the time, or `SOURCE_DATE_EPOCH`), reading only the manifest and the SBOM; `inspect` says the coverage (`sbom_coverage` in the JSON) without reading the tree. No new dependency (the JSON is written by hand). Specification §3.1.12 and §7.3, 5 conformance fixtures (150/150, the independent verifier and the Rust side), 9 unit tests, `tests/sbom.py`. Limits: the document names libraries by SONAME and hash, not by upstream name and version (that comes with the recipes); plugins and programs without a SONAME are not listed; an author cannot give an SBOM of their own yet.
- **Step 9, PR 7: `permissions.devices` is a list of categories.** Before: a boolean that lets the app open the uevent socket of netlink, so the permission could not say what kind of device the app is for and could not grow (a game pad, a camera, an input device and a USB device would each need their own file access) without changing its type after the format is frozen. Now (PANPAK-FORMAT.md §3.1.5): `devices = [\"gamepad\", \"camera\"]`, one to four different names. The boolean of the test versions is refused by `pack` with a message that says what to write, and does not parse in a package; an empty list and a repeat are a malformed field; a name that this panpak does not implement, including the reserved `input` and `usb`, is \"update panpak\". **What a category does today:** each gives exactly what the boolean gave, the hot-plug notices (the uevent socket), and **no category gives access to a device file**; the sentence of the permission names the categories (\"Be told when devices are plugged in or removed (game pads, cameras)\", Attention, English and Italian) and still says that the notices are those of every device of the machine. A category is implemented, and the access to the files of its type added, only when an app of the harness uses it for real: that needs a game pad or a camera, which this machine does not have, so none was added here; the camera of a window of a desktop is `portal.camera`. The conformance suite has 6 new fixtures (a list, the boolean, an unknown name, a reserved name, an empty list, a repeat) read by the independent verifier and by the Rust side (145/145). Tests: `validate.rs` (the list, the refusals, the boolean), `permissions.rs` (the row), `tests/hardening.py` (the uevent socket with `[\"gamepad\"]`, and `pack` refusing the boolean, a reserved name, an unknown name, an empty list and a repeat). No compatibility: a package with `devices = true` is made again with `devices = [\"gamepad\"]` (or the category that fits).

Since PR 4 the key of a package is in `[trust].root`, which the text edit did not touch, so every package it made had a signature that did not match its own root and `install` said `PANPAK-E1001`; the benchmark printed \"not installed here\" and a guess (a missing library) for it, and `docs/BENCHMARKS.md` kept the guess. Tests: `panpak/tests/host.rs` (`resign` and the bus), the unit test of the core, `tests/incremental.py`, `update_footer.py` and `background.py` with the new `resign`.
- **Step 9, PR 6: `[host]`, what a package needs of the system.** Before: the only requirement a package could state was `[abi].glibc_min`, an app that needed a newer kernel, a Landlock ABI, a display server or a portal installed and failed at the first start with whatever message the loader or the sandbox gave, and `install` could not say that a package was made for another architecture. Now (PANPAK-FORMAT.md §3.1.11): (1) a critical table `[host]` with `arch` and `glibc` (written by `pack`: the architecture of the machine that packs, and the highest glibc symbol version of the files, which an author may raise; `[abi].glibc_min` moves here and is gone from `[abi]`), and, given by the author, `kernel`, `landlock` (1 to 9), `display` (`x11`, `wayland`; one is enough), `portals` (`document`) and `bus` (`none`, `private`). A value that is not of the form is a malformed field; an architecture, display, portal or bus that this panpak does not know is \"update panpak\", and so is an unknown key. The name `host_contract` is reserved and has no meaning yet. (2) **Two kinds of key.** `arch`, `glibc`, `kernel` and `landlock` belong to the *machine*: `install`, `update` (before anything is downloaded, also for a version that is only staged) and `doctor <package>` refuse a package that the machine cannot run, listing every requirement that is not met as what is needed, what is there and what to do (`PANPAK-E2009`; the glibc keeps `PANPAK-E2005`). `display`, `portals` and `bus` belong to the *session*: an install over ssh, from a script or in the build of an image has none of them and must work, so install and update never look at them; the **start** of the app does, with the same three parts (\"cannot run in this session\"), and it is not forced. `doctor` says, as a note and not a failure, what the current session lacks. (3) `--force-host` of `install` and `update` is for the machine: it goes on and says what is missing; the choice is kept as `forced_host=1` in `apps/<id>/trust`, so an update does not need it again, `doctor` keeps listing what is not met (\"installed with --force-host\"), and a version that the machine can run clears it; an app that was forced is not refused at the start for `landlock`. (4) The start reads only what the package names (nothing, for a package that names none of `display`, `portals`, `bus`, `landlock`). (5) **The messages are in the catalog** (`HOST_*` in `messages.rs`, English and Italian in `po/it.po`: the parts of each requirement, the heads, the hint about `--force-host`, the note of `doctor`); the names (`glibc`, `Linux`, `Landlock`, the display servers) are not translated. (6) The independent verifier and 9 new conformance fixtures read the table (139/139 with the Rust side). No compatibility: a package made before this change has its glibc under `[abi]` and is made again. Tests: `host.rs` of the core (what is met, each unmet requirement with its parts and its code, the two scopes, a start without a display, a system whose glibc cannot be read, the forms), `panpak/tests/host.rs` (pack writes the architecture and refuses one given by the author and the old `[abi]` key; install refuses the machine with the three parts and never for the display, `--force-host` goes on, `doctor` keeps saying it and notes the session; an install with no display works and the start without one is refused, in English and in Italian), `pack_checks.rs` (glibc), the conformance suite. `tests/startup_budget.py --host` measures a package that names a display and a Landlock ABI; `tests/UNSTABLE.md` lists the tests that failed once and then passed and tells the rule (a second failure is investigated first). Its first case was `pty.py`, which failed in the full suite three times and never alone: the suite had been started as a background command of a non-interactive shell, which makes SIGINT ignored for everything it starts, and the ignore is inherited through `exec`, so Ctrl+C did not stop `sleep 30` in the shell of the test. Reproduced at once by running the test with SIGINT ignored; the child of the pty now puts the signal back to its default.
- **Step 9, PR 5: the index says what each file is, the modules are reported by `pack`, and `allow_missing` is gone.** Before: `inspect` and `doctor` opened the tree (or the chunks of the package) to know which files are ELF files, what their SONAME is and which scripts set `LD_LIBRARY_PATH`; the inventory of a package that was not started yet was by file name only; and an author (or the harness, in a loop of `convert` and `doctor`, up to 60 rounds) listed by name the libraries that nothing provides (`--allow-missing`, `[abi].allow_missing`), a judgement that nobody verified: on five apps 97 libraries were unresolved and none was asked by a file that a program reaches. Now: (1) every file entry of the **signed index** has `flags` (bit 0 ELF, bit 1 a script that sets `LD_LIBRARY_PATH`, bit 2 a SONAME follows; the other bits are 0 and a reader refuses a package that sets one), the SONAME, and an **extension area** (entries `u16 type, u16 length, data`, none defined; the top bit of the type makes an entry critical, so a field can be added after the freeze without a new format). `inspect`, `doctor` and the inventory of an uninstalled package read the index only. (2) **The report of the modules** (`.panpak/modules`, a text file of the tree whose hash is `[abi].modules`; PANPAK-FORMAT.md §7.2): `pack`, `convert` and `build` read the ELF files, take the programs (executables with an interpreter, no `.so` in the name), follow `DT_NEEDED` through the libraries of the tree, and write which libraries the programs need (*required*) and which only modules need and the tree lacks. A required library that nothing provides is an error where the app starts, as before; one that only modules need is left out and the app starts, and `inspect` lists it as "not available on this system" (`modules_not_available` in `--json`). Nothing is declared optional by anyone: `--allow-missing`, `[abi].allow_missing` and `collect.allow_missing` of a recipe are removed (`--allow-missing` says why it is gone), and the harness converts once instead of in a loop. A library that is present is now decided like any other even if only a module asks for it (before, `allow_missing` skipped it even when present). The report is text, not JSON, because the core has no JSON reader and a line format is simpler to verify. Its first line is `panpak modules 1` (the version of the form: a reader refuses a higher one with "update panpak"), and PANPAK-FORMAT.md §7.2 gives the grammar (ABNF, groups in order, ascending byte order without repeats, a writer gives the same bytes for the same tree). (3) **Texts** (English and Italian, `po/it.po`): the notice of a change of signing key and of a recovery say what happened to the person and that nothing is to be done, with no key in the sentence (the key is in `panpak inspect`: a `key:` line); the doctor line for a change of channel says it in plain words and the app and the note follow on the next line; `panpak key new` says above the 24 words that they are not a wallet seed. (4) **No test reaches the session bus of the real user.** Tests that ran with an isolated HOME but inherited `DBUS_SESSION_BUS_ADDRESS` sent notifications ("Rel is updated") to the real desktop. Now: `tests/isolation.py` (`require_isolated_home`, which every test of the suite calls) sets an address that leads nowhere; `tests/with_timeout.py`, which runs every script and the `cargo test` of the CI, puts a *canary* in `XDG_RUNTIME_DIR/bus` and fails the run, naming the program, if anything connects to it; the Rust tests set the address in their command builders; and a debug build of `panpak` or of the stub that runs with a HOME that is not the real home and reaches `/run/user/<uid>/` stops with status 97 (`guard_real_bus`). `tests/bus_guard.py` checks the runner. (5) **The end of protected mode is told only to an app that was in it.** `mode_ended` used the floor that the same command had just seen to decide that the old version "was" in the mode, so a package that raised its own floor, installed over an app that never ran in the mode, said "The problem is fixed and the internet works again". Now it is told only when the mark of the mode was there before the command saw the floor; the leftovers of the mode are cleared in any case. Test: `the_end_of_protected_mode_is_told_only_when_the_app_was_in_it` (an ordinary update, a package that is its own fix, an app in the mode, an update after it). No compatibility: a package made before this change does not parse (the index entry of a file is longer) and is made again. Tests: `modules.rs` (the report, its text, a tree with no program), `the_inventory_from_the_index_takes_files_with_so_in_the_name` (by name and by SONAME), `pack_checks.rs` (a library that only a module asks for, and one that a program asks for), the conformance suite (8 new fixtures for the flags, the SONAME and the extension area; the independent verifier reads the new entry; Appendix A redone), `tests/trust_update.py` (the new texts), the app harness (one conversion).
- **Step 9, PR 4: `[trust]`, keys that can be recovered, and a first install that says whom it trusts.** Before: the key of a package was `[update].key` and a rotation was one signature of the old key; the first install trusted whatever key came with `--yes`; a stolen signing key could not be undone; the key was made by itself the first time a package was signed; `apps/<id>/pinned-key` and `apps/<id>/floor` were two files. Now: (1) **`[trust]`** (critical, written by `pack`): `root` (a list, one key for now), `threshold = 1` (more is reserved and refused with "update panpak"), `recovery` (`blake3:` the hash of the recovery public key, from the first package), `domain` (optional, checked against the app id: `example.org` for `org.example.app`) and `chain` (at most 8 successions). `[update].key` is not part of a package any more (an input that has it is accepted when it matches the signing key). (2) **Succession** (`PANPAK-FORMAT.md` §3.0, §3.2): a step signed by the root that was keeps the recovery commitment; a step signed by the recovery key (revealed) sets a new one and is valid from any pin with that commitment, so it wins over a thief's succession; the message names the app, who signs, the keys and the next commitment (label `panpak/succession/v2`). The client follows the chain from its pin, ignoring the steps before it. (3) **`panpak key new [-o file]`** makes the signing key (0600), the commitment beside it (`<file>.recovery`) and shows the recovery key once as 24 words (the English word list of BIP-39 with its check, so any tool that reads BIP-39 can check a phrase; the words are not kept); `keygen -o` is the same. **A key is never made by itself**: `pack`, `build` and `convert` without one stop with `PANPAK-E1000` and name `panpak key new`; one without a commitment says so (`--recovery`, `PANPAK_RECOVERY`). `pack --rotate-from-file` and the new `--recover-with <words>` make a succession, and **the chain is kept beside the signing key** (`<key>.chain`, by app id, because a succession is signed for one app): `pack`, `build` and `convert` put it in every later package with no option, and name the recovery commitment where the chain ends; `pack --sign-command <cmd> --public-key <key> --recovery <hash>` signs with an external command (it gets the bytes on its standard input, writes 64 bytes; the signature is checked against the key before it is used). (4) **The first install says whom it trusts**: `--expect-key <key>` (another key: `PANPAK-E1004`, nothing pinned, nothing made ready, `--yes` or not) or `--trust-first-key`; `--yes` alone is refused (`PANPAK-E1003`); an interactive terminal still gets the question. (5) **`apps/<id>/trust`** (`key=value`) replaces `pinned-key` and `floor`: `root` (two lines while a key is replaced), `recovery`, `source` (`author`; a catalog or a distribution is reserved), `floor`, `seen_revision`, `switch_note`, and reserved `hold` and `confirmed`. (6) **Where updates come from** is said at the first install ("Updates: from <host>, named by the author." or "This app does not update itself: ..."), in `list` (a new column and `"updates"` in `--json`) and in `doctor`, in English and Italian. (7) A change of channel that takes **the same revision with other bytes** is noted in `trust` (`switch_note`) and `doctor` says it is an error of the author. Tests: `trust.rs` (unit), `tests/trust_update.py` (key new, the first install, a succession, a thief, the recovery words, a wrong word, the channel note), `panpak/tests/convert_icons.rs` (no key made by itself), `failpoints.py` (the rotation, interrupted at every point), the conformance suite (13 new fixtures; the independent verifier checks `[trust]`), `fuzz_rotation` (the chain).

- **Step 9, PR 3b: protected mode.** A version that the author has put below a floor (a revision below which nothing should run as it is) was either kept running as before or, if a client blocked it, would cut the person from the app and the data. Now it is not blocked: it starts **with no network but its own loopback** (no TCP, UDP, DNS, QUIC or IPv6: in the view it is the empty network namespace of an app with no network permission, and without a view a filter of the system calls refuses every IP socket: `seccomp::build_options`), **without running programs that it wrote**, and **without opening addresses** (`xdg-open` and OpenURI, a way for data to leave in the browser; the app fails and **the person is told**: a notification, or one line, "<App> is in protected mode: links do not open until you update", at most once in 20 seconds; tested through the filtered bus in `tests/privbus.py` scenario P; without a view the system's `xdg-open` stays reachable by the app and the addresses are not stopped). The floor that a client has seen for an app is kept in `apps/<id>/floor`; the file `apps/<id>/protected` marks the apps in the mode, so that a start looks for one file only. The manifest is changed in memory, never the signed one. The person is told at every start in the way that fits how the app was started, and never has to type a command: a program with windows gets a notification, with the button "Update now" only when an update that fixes the problem is ready (it opens the window of `zenity` or `kdialog`, as the menu action "Uninstall" does, with the new permissions); a program of the terminal started from an interactive terminal is asked there with one key (the update, then the internet); a start with nobody to ask gets one line. The menu of the app has the action "Turn the internet back on…" while the mode lasts. All the logic is in one place (`panpak/src/protected.rs`) and readable as JSON (`panpak protected --json`, `panpak protected-action`), so the Panpak app (step 10b) can replace the notification, the windows and the questions. `panpak allow-internet` and `panpak update` stay for scripts. The mode ends by itself when the fixed version is put in place, with a message; an update accepted while a copy ran is applied at the next start without asking again (`pending-state` has `accepted`). All texts are in English and Italian (`panpak-core/src/messages.rs`, `po/it.po`). `Permissions` derives `Default`; `startup_budget.py --protected` measures a protected start. Tests: `tests/protected_mode.py` (a real start in the view, and again with the view masked, with TCP, UDP, DNS, IPv6, an address and a written program, before, in the mode, with the internet back on, after the fix; the questions on a pseudo terminal; fails on main: a version below the floor still reaches all of them), `tests/protected_ui.py` (the notification service and the windows faked: the button only with an update ready, the permissions window, a copy running, the menu action, the terminal, the JSON actions), `panpak/tests/protected.rs`, unit tests (seccomp, release, stub, opener, desktop entry).
- **Step 9, PR 3a: the `[release]` table, the checks when a package enters, and `.panpak/history`.** Old and new were told by comparing version texts (`1.0-rc1`, suffixes), `install` of a file over an installed app compared nothing at all, a republished version with other bytes and the same text was ignored, and nothing said "this version is withdrawn". Now every package has a `[release]` table: `revision` (a number that grows with every release of a channel; the only thing a client compares), `floor` (nothing below it is installed, updated to or rolled back to, not even with `--allow-downgrade`; only grows), `security` (the latest revision that fixed a vulnerability: `record::security_mark` is now real, `security > installed revision`, a number and not a yes or no so that a skipped version does not lose it), `channel` (`stable` by default; fixed at install), and `history`. Written by `panpak pack` from the author's `[release]` in `panpak.toml` (all optional; revision 1 by default) and from the earlier package: `pack --previous <package>` makes revision +1, keeps the highest floor and security, and writes **`.panpak/history`**, a file of the tree (so the signed index covers it, and `[release].history` names its hash) that lists the earlier releases of the channel (revision and hash of the signed message). `convert` and `build` follow the installed version of the same app when it has the same key (the revision after it), which is what a re-conversion of the same AppImage after an install gives (a different package, on purpose). `install` over an installed app, `update`, `apply` and the staging all check: another channel is refused (`PANPAK-E4005`, `--switch-channel`), a revision below the highest floor seen for the app (`apps/<id>/floor`, kept even when the update goes no further) is refused (`PANPAK-E4003`), a lower revision is a downgrade (`PANPAK-E4001`, `--allow-downgrade`, new for `install`), the same revision with other bytes is a fork or a replay (`PANPAK-E4004`, with the way out in the message), and a package whose history does not continue the installed one, or drops the history that the installed one had, is refused (`PANPAK-E4006`; at an update the downloaded record is taken away, at an apply the staging). `panpak rollback` to a version below the floor is refused. The history is read only when a package enters, never at a start. `[release]` is a critical section. The version text decides nothing any more; the `PANPAK-FORMAT.md` §3.1.10 has the rules. The app harness (`tests/apps`) writes a digest of the permissions of each package in its result and `tests/apps/compare.py` refuses to compare two runs that do not ask for the same permissions. The vectors, the independent verifier (`conformance/verify.py`), 8 fixtures and Appendix A are redone. Tests: `release.rs` (six tests: the chain with its history, the rules of `pack`, an older revision, a fork, the floor, the channel, a history that does not continue), `tests/release_update.py` (the same over HTTP: update, staging, apply, rollback, the security mark, the floor kept), the unit tests of `release.rs` of the core, `CompareRuns` of the app harness.
- **Step 9, PR 2: the `[format]` table, and the absolute library list is gone.** Defect 42: a reader skipped a manifest field that it did not know, so a field added later to restrict an app would have been ignored by an older panpak, and the app would have run with less confinement than declared. Now every package has a closed `[format]` table, written by `panpak pack` and signed: `min_panpak` (an integer level, 1; it goes up only when the meaning of something that exists changes), `critical` (the fields that change what is safe, as `permissions.network`, `launch.env`, `env`: written from the sections that `pack` knows, so it cannot be forgotten), `compression = "zstd"`, `chunking` and `packed_by` (informative, signed). A reader that does not know the level, the compression or one critical path refuses with `PANPAK-E0002` and "update panpak"; the client (`install`, `update`, `doctor`) and the runtime that starts the app both check it, because both call `verify`. A package without `[format]` is refused with the new `PANPAK-E0011` ("made with a test version of panpak: make it again") before its signature is checked, so it is not told that the signature is bad. An unknown key in `[format]` refuses the package; `pack` refuses an input that has a `[format]` table. A section of the manifest has to be classified (critical or not) in `SECTIONS`. Also the fallback to an absolute `LD_LIBRARY_PATH` for a package without the `.panpak-lib-<h>` mark is deleted: a package whose entry is a program and that has no mark is refused (`PANPAK-E0009`, "make it again"); one with no program gets no `LD_LIBRARY_PATH` from the runtime. The bundled loader keeps `--library-path` (an argument, not inherited). **The list is derived and checked for completeness.** Every function that signs a manifest makes `critical` again from the manifest and `SECTIONS` (`pack`, therefore `convert` and `build`; `with_recomputed_critical` for a tool that edits a manifest and signs it again; the app harness and the Rust and Python test signers use it), and nobody writes it by hand; a list that was there is replaced (not refused: it is derived data and the result is the same either way, while refusing would stop the harness for no gain in safety). The reader checks that the list is complete for the fields it knows: a manifest that uses a field of a critical section that the list does not name is malformed and refused with the new `PANPAK-E0012`, in `verify`, so for the client and the runtime. Without this, a restricting field added after `pack` and signed with the old list would hide from an older panpak (defect 42 by a side door). `[runtime]` is a critical section, so `runtime.stub_hash` is in every list. The vectors, the independent verifier (`conformance/verify.py`), 13 new fixtures and Appendix A are redone. - **Step 9, PR 1: the signature covers a labeled message, and the 64 bytes of signature become a signature block.** Before: the key signed `manifest || root` with no label, the footer `version` and `flags` were outside the signature, a succession signed the 32 bytes of the new key (one signature valid for every app of the same key), and there was no room for anything but 64 bytes after the manifest. Now: (1) the package message is `"panpak/package/v1\0" || u32 version || u32 flags || root || manifest`; (2) a succession signs `"panpak/succession/v1\0" || app id || old key || new key`, so it belongs to one app; (3) after the manifest comes a **signature block**, a list of entries `u16 type, u16 flags, u32 length, data`: type 1 is the package signature (exactly one, critical); an unknown entry is ignored unless its critical bit is set, and then the package is refused with "update panpak"; types 2, 3 and 4 (transparency proof, another algorithm, a countersignature) are reserved; flags other than the critical bit, a block over 64 KiB, an extra byte and a repeated signature are refused. The footer is unchanged (80 bytes; the block runs from the end of the manifest to the footer), so an update still reads footer, manifest and block with two small Range requests. No compatibility: packages made before this change do not verify (the format is not frozen and there is no installed base). - **Icons are cleaned by `pack` and `convert`.** Real PNG files carry text, profile, gamma and other chunks that `install` does not accept. `pack` and `convert` now
  keep only `IHDR`, `PLTE`, `tRNS`, `IDAT` and `IEND` (byte for byte; the pixels and the transparency are not touched), print the chunks they removed from each icon, and
  `install` stays strict. `pack` puts the cleaned icons in the package as generated entries `.panpak/icons/<side>.png` (the signed manifest points there); `convert` reads the icons
  (links followed only inside the tree) and hands them to `pack` in memory: it writes no icon file. `.panpak/` is the folder that only `pack` writes.
- **`convert` no longer writes through links of the AppImage.** The unpacked tree is a private `mkdtemp` folder, and every write to it (files, folders, links, the wrapper
  scripts and `panpak.toml`) goes through folder descriptors that do not follow links. Before, an AppImage with `bin -> /somewhere` or `panpak.toml -> /some/file` could make
  `convert` write outside its folder.
- **The user's `hicolor` icon theme is not in the view of the app.** The menu icons that `install` writes there made Qt apps start 60 to 110 ms later (no `icon-theme.cache`: 40,000 failed lookups). The app still reads the
  other theme folders of `~/.local/share/icons` and `~/.icons`.
- **A stable `panpak` and a stable stub.** The store has `bin/panpak-stub` (a link to the best runtime) and `bin/panpak`. Launchers run the stub
  through the link, so a new runtime reaches every app at its next start, and the menu action "Uninstall" runs `bin/panpak`: no launcher or
  entry names the folder from which `panpak` was run any more. `install-runtime` writes both with a rename; `install` copies `panpak` when there is none and warns when the one in
  the store is older. `panpak --version` prints the version.
- **The menu entry is thin and versioned.** The entry is made from a fixed template (the keys it may have are tested) and carries
  `X-Panpak-Desktop-Version`. When an app starts and its entry or launcher is older, the runtime rewrites both (temporary file, `fsync`, `rename`); when
  there is nothing to do it costs 0.04 ms.
- **`panpak remove` and `panpak list` say more.** `removed <id> <version>: freed <size>`; a second `remove` (or an unknown id) says "not installed:
  nothing to remove" with `PANPAK-E2004`; `list` of an empty store says how to install.
- **The menu entry and GNOME Shell.** Tested on GNOME Shell 50: a new or changed entry (and its icon) shows about 5 seconds after the file changes, with nothing but the
  `rename` panpak already does; an app that was already started from the Shell in the session keeps its old entry until the next login. `install` and `update` say so when
  they replace an entry with a different one.
- **The desktop's own scope is recognised for every launcher.** The shortcut that skips the scope of the app follows the portal's rule for scopes
  (`app-gnome-panpak.<id>-<n>.scope`, `app-panpak.<id>-<n>.scope`), with the systemd escape; the unit is the one `sd_pid_get_user_unit` finds, so a process in a sub-cgroup counts.
  A service (`app-...@<n>.service`) does not get the shortcut: a portal older than 1.21 may not read services, so the runtime makes its own scope, as from a terminal.
  `tests/dbus_filter.py` runs the three shapes against the real portal.
- **`install` and `update` warn about unknown fields.** A signed package that has manifest keys this panpak does not know is still installed (they are ignored), with a
  warning that says to update panpak (`panpak install-runtime`).
- **A key that this panpak does not know** in a `panpak.toml` given to `pack` or `convert` is still refused, now with `PANPAK-E0008` and a message that says it is a
  misspelling or a field of a newer format, and how to get a newer panpak (`panpak install-runtime`).

- **Hardening of the app process.** Every app now starts under a seccomp filter (a deny list, installed last, with
  `no_new_privs`; it returns errors, it does not kill): `io_uring`, `bpf`, `userfaultfd`, `perf_event_open`, the key ring,
  `ptrace` and `process_vm_*`, the mount calls, `setns`, new namespaces through `clone` and `unshare` (user namespaces too), `clone3` (`ENOSYS`),
  terminal input injection, odd `personality` values and the non-native ABIs are refused; the table with the reasons is
  PANPAK-FORMAT.md §9.8. New error code `PANPAK-E3002` (no seccomp). **Programs that need a user namespace of their own (Chromium and
  Electron sandboxes, WebKitGTK, `bwrap`, `flatpak`) cannot run in the view.** The device ioctl right (Landlock V5) is kept only on `/dev/tty` and `/dev/dri`.
  `/var/cache/fontconfig` is read-only in the view: the first start with an empty private font cache went from 446 ms to 48 ms with `fc-match`.
- **Wayland security context.** With a compositor that offers `wp_security_context_v1` (KWin, Sway and the other wlroots compositors),
  the app gets a socket of its own that the compositor knows as sandboxed (engine `io.github.panpak`, app id `panpak.<id>`). GNOME's compositor does not offer it:
  the app keeps the normal socket and `panpak doctor` says so. The client is part of `panpak-core` (no new dependencies) with the fuzz target `fuzz_wayland`.
- **The open-address channel is read by a receiver with no rights.** The resident stub is now two pieces (PANPAK-FORMAT.md §9.7): a receiver process
  (Landlock with no rule, a seccomp allow list, limits) reads what the app sends and passes validated requests as frames to the actor, which checks them again.
  Fuzz target `fuzz_receiver`.
- **The `audio` permission says that it includes the microphone** in the text of `install` and `update`; it was already so, and it is a known limit (KL-30).
- **Faster start.** The fixed cost of a start (measured against running the program directly) fell from 40 ms to 25 ms without the filtered session bus and from 56 ms
  to 38 ms with it (26 ms when the desktop started the app in a scope that already names it, as the GNOME menu does: then no scope is made): the `gsettings` queries, the systemd scope and the proxy overlap the work of the start, the inner stub waits for the proxy's socket, and the version of the proxy is remembered between starts. The app and the proxy are always in a scope that gives the app its identity.
  `PANPAK_DEBUG` prints where the milliseconds go. `tests/startup_budget.py` measures it and runs in the CI as an advisory step.

- **`panpak list` and `panpak remove`.** `list [--json]` shows the installed apps (id, name, version, disk space of the
  app and of its data, status, including incomplete installs). `remove [--purge-data] [--yes] <id>` takes away the launcher,
  the desktop entries panpak wrote, the packages, the trees and the shared `/tmp` of the app; the settings and data stay
  unless `--purge-data` is given and confirmed. It refuses while a copy is running (`PANPAK-E2002`), never follows a link,
  moves the app folder aside with one rename and is finished by the next command if it is interrupted
  (PANPAK-FORMAT.md §9.6, THREAT-MODEL.md §2.4). The desktop entry gets the action "Uninstall" (`panpak remove --ask <id>`: a dialog with zenity or kdialog, a notification at the end). A start waits for a removal in progress and ends with `PANPAK-E2004` when the app is gone. New error codes `PANPAK-E2002` to `E2004`; the fuzz targets `fuzz_dbus`,
  `fuzz_dbus_names` and the new `fuzz_journal` run in the CI smoke job.

- **A filtered session bus for apps in the isolated view.** With `xdg-dbus-proxy` (0.1.5 or newer), a systemd user
  manager and the view, an app gets a session bus that reaches only: the appearance and inhibit portals, its
  own `app.id` (single instance across copies), and, if the manifest asks, notifications, a tray icon and up to 8
  declared names (`[permissions] notifications`, `tray`, `dbus_own`). Every other interface and name is refused.
  The outer stub moves itself into a systemd scope `app-panpak.<id>-<n>.scope` so that the portal knows the app as
  `panpak.<id>`, and the folder `doc/by-app/panpak.<id>` of the document portal is in the view. Without the parts the
  app has no bus, as before; `panpak doctor` reports it. See PANPAK-FORMAT.md §3.1.5 and §9.5, THREAT-MODEL.md §3 and KL-5, KL-23 to KL-27.
- **The desktop entry is `panpak.<id>.desktop`** (it was `<id>.desktop`) and carries `StartupWMClass` when the manifest has
  `[desktop] wm_class`. `install` and `update` remove the entry of the old name when panpak wrote it. After an update,
  the launcher of an app is found under the new name in menus and the dock.
- **Quiet start.** The lines about `allow_missing`, libraries taken from another copy and undefined symbols are no longer printed
  at every start; they appear with `PANPAK_DEBUG` set. `install` lists the excluded libraries once and `doctor <package>` checks the symbols.
- `install-runtime` replaces the runtime by a rename (open apps are not disturbed) and takes the flags before or after the file.
- In the isolated view, writable folders get the Landlock `Refer` right, so a rename between folders works (Qt local sockets).
- New command `panpak dbus-rules <package>` prints the arguments the stub gives the proxy.
- A small D-Bus client for the outer stub in `panpak-core` (no new dependencies), with the fuzz targets `fuzz_dbus` and `fuzz_dbus_names`.
- **No network means no network in the isolated view.** An app whose manifest asks for no network (`network` not
  true, no TCP port) runs in a network namespace of its own with only the loopback interface, so it can no longer
  send UDP datagrams or look names up; before, Landlock stopped TCP only and UDP went out. The resolver socket
  of systemd is in the view only for apps that ask for network. Without bubblewrap nothing changes: UDP is still
  open (see THREAT-MODEL.md).
- **Fix: Landlock V9 rules were dropped on the musl build.** The rules for the sockets every app may reach
  (journal, Wayland, resolver, audio) and for `sockets_allow` were left out without a message, because
  `landlock::PathFd` opens files with the standard library, which drops `O_PATH` on musl. On a V9 kernel the
  journal socket was refused. Every rule now opens its path with `O_PATH`; a rule left out for any reason
  other than a missing path prints a warning, the fallbacks for `/dev` say why they were used, and
  `panpak doctor` lists rule paths that cannot be opened.
- **Fix: sockets outside `/run`, `/tmp` and the home folder.** The root of the isolated view is a new tmpfs with
  only `/usr`, `/etc`, `/sys`, `/dev`, `/proc`, the Nix and Guix stores and the top-level links, so a socket
  in `/var`, `/opt`, `/srv` or the folder of a container manager is not in the view.
- **Fix: stale lock files in the view.** The app is always process 2 in its own PID namespace, so lock files
  with a process id (Chromium `SingletonLock`, Qt `QLockFile`, Firefox `lock`) never expired. The runtime now
  removes the ones it recognises by content, in the app's private folders only, when no copy is alive and the
  mark `userdata/<id>.in-use` shows that the last run did not end normally. New command
  `panpak data unlock <id>`.
- **Fix: `panpak convert`.** The manifest is validated with the rules of `install` before it is signed;
  a `DT_NEEDED` entry with a path is not a library name; the string table limit follows the file instead of a
  fixed 1 MiB; the loader symbols are no longer reported undefined when `ldconfig` is not in `PATH`.
- **Fix: processes started after a fork.** Between `fork` and `exec` the opener and the socket probe call
  only async-signal-safe functions, so a start made while other threads allocate cannot hang.
- **Documentation.** `SECURITY.md` uses GitHub's private vulnerability reporting; `THREAT-MODEL.md` has one
  list of known limitations; `docs/BENCHMARKS.md` and the scripts in `bench/` give reproducible measurements.

- **Fix: first starts at the same time.** Two starts that overlapped on a store without the tree could end with
  `PANPAK-E2000: No such file or directory`, because they built in the same `.partial` folder. The tree is now
  built under an `flock`, in a folder apart, and published with one rename; the others wait and then use it.
  The problem was in the first version of the stub, so it exists in every earlier release.

- **User folders: `[[permissions.xdg_dirs]]`.** An app can ask for the music, documents,
  pictures, videos or download folder of the user, `ro` or `rw`. `install` and `update` find the
  folder in `~/.config/user-dirs.dirs` with a strict parser, refuse unsafe places, show it
  (`music: ~/Music (rw)`) and pin it; at start the folder is granted only if it still matches. The app gets a
  private `user-dirs.dirs`. In the isolated view the home folder can be listed.
- **Opening links from the isolated view.** `xdg-open` (and GIO, Qt and Electron through it) in the view
  asks the outer stub over a private socket, which passes on `http`, `https` and `mailto` addresses only
  (with only the plain `mailto` fields), at most 5 per second. The stub now stays running while the app runs.
- **URL schemes: `[desktop] schemes`.** The `.desktop` file declares `x-scheme-handler/<scheme>` and runs the
  launcher with `%U`.
- **Copies of one app** share a `/tmp` and a `/dev/shm` of their own in the isolated view; a start with no
  copy alive empties them. Two copies still do not see each other's System V IPC without `x11`.

- **Private folders for each app.** The stub gives every app its own
  config, data, state, tmp and cache folders (mode 0700, outside the store) and
  points `XDG_*`, `TMPDIR` and `SQLITE_TMPDIR` at them. Writes go only there,
  to `/tmp` and to the `home_paths` of the manifest. The app can read the
  user's theme, font and icon settings and nothing else of the real config.
  `~/.local/share/<id>` is no longer used and is not migrated: move the files
  by hand with `panpak data path <id>`. New commands `panpak data path|clear`.
- **Manifest: `[launch]` and `permissions.home_paths`.** Extra start arguments
  and environment (with placeholders for the private folders), and fixed home
  paths as a last resort. `install` shows the permissions; `update` asks before
  it adds any. A package that asks for the D-Bus socket gets a warning.
- **Local sockets.** The stub removes `SSH_AUTH_SOCK`, `GPG_AGENT_INFO` and
  `SSH_AGENT_PID` and sets `DBUS_SESSION_BUS_ADDRESS` and `DBUS_SYSTEM_BUS_ADDRESS` to `disabled:` (each unless the
  manifest lists that bus). `doctor` shows whether the kernel can isolate
  an app from local sockets, and `install` and `update` warn when it cannot.
  `install` over an installed app asks before it adds permissions.
  `--yes` no longer accepts new permissions: use a terminal answer or the new
  `--accept-new-permissions`. `gsettings` is looked for only in `/usr/bin` and
  `/bin`.
- **Socket probe** (`PANPAK_SOCKET_PROBE=<log>`), a measurement mode, never on by default:
  the stub supervises the app and logs its socket and namespace calls. It blocks nothing.
  `DBUS_SYSTEM_BUS_ADDRESS` is hidden like the session bus. See docs/SOCKET-PROBE.md.
- **Isolated view (bubblewrap).** If `/usr/bin/bwrap` works, the app runs in a view with `/` read-only,
  an empty home folder (only the app folders, `home_paths`, the readable settings, the tree and the stub
  come back), a private `/tmp` (`TMPDIR=/tmp`, which also fixes the long-path crash of Simplenote), a `/run`
  and a runtime folder that hold only the allowed sockets (Wayland, journal, resolver, the `sockets_allow` list),
  its own process list and, without X11, its own IPC namespace. Inside it the session and system buses,
  systemd of the user, gpg-agent and ssh-agent do not exist. Landlock is applied on top. Without bubblewrap
  the start is as before. New manifest key `permissions.audio` (PipeWire and PulseAudio sockets).
  `socket_isolation` now reports the active layers; `doctor`, `install` and `update` show them, and `doctor`
  says why the view is unavailable and how to fix it. `sockets_allow` also works on kernels below Landlock V9
  when the view is available. Landlock V9 gets `ResolveUnix` rules for the same sockets (tested on Fedora 44,
  kernel 7.2.7; see the fix below).
- **Libraries: the bundle first.** When a library is in the package, the package copy is used, except for
  glibc and the graphics stack (which must match the system and the driver) and for `libstdc++` and
  `libgcc_s` (the copy with every symbol version the app needs). A library that is not in the package comes
  from the system, as before. This fixes `symbol lookup error` with a system library of the same name and a
  different API (Audacity and `libSoundTouch.so.1`). `panpak doctor` checks, for an installed app, that the
  symbols it needs are defined by the chosen libraries. The format does not change. See PANPAK-FORMAT.md §7.
- **Libraries: families and a symbol check.** GLib, GTK (with GDK, Pango, Cairo and the like), GStreamer and FFmpeg move
  whole, as Qt already did: all from the package or all from the system. After the rules, the runtime looks for symbols
  that no chosen library defines and, if it finds some, takes the library (with its family) from its other copy, until
  nothing is missing or nothing can change (at most 8 steps). If some remain, the app still starts, with a warning, and
  `panpak doctor` lists them. This fixes QOwnNotes, whose bundled GLib was older than the system libraries it also loads.
- **Resolution cache and speed.** The cache of the library resolution is now keyed by the package root and its `[abi]`
  fields, the stub, the kernel, `/etc/ld.so.cache` and the identity of every system library the decision looked at (also
  the ones not chosen) and of the loader, so an update of `libglib` or `libcrypto` makes the next start resolve again.
  A hit no longer hashes the package or runs `ldconfig`. The ELF files are read once each with `pread`, only the sections
  that matter, on several threads: the resolution of Kdenlive (449 libraries) takes about 40-140 ms instead of 1.2-1.4 s.
- **GTK3 dark theme** from `gsettings` at start (at most 200 ms).
- **Security: paths and text from the manifest.** `app.id` has one strict
  grammar (spec §3.1.1) and every manifest field that becomes a path, a file
  name, a `.desktop` line or terminal text is checked in `verify`, so a signed
  package cannot make `panpak` or the stub write outside the store (new codes
  `PANPAK-E0006`, `PANPAK-E0007`). `rollback` and `open` check the id they are
  given. Index paths and symlink targets reject control characters.
- **Security: launchers and `.desktop` files.** Written through a temporary
  file and a rename, never through a symbolic link, and only over a file that
  Panpak wrote for the same app (`PANPAK-E2001`). Values are escaped as the
  Desktop Entry Specification requires and the `Exec` path is quoted.
  `panpak convert` escapes the strings it copies from an AppImage.
- **Test and bench scripts** refuse to run when HOME is not inside their work
  directory and never delete outside it; `bench/campaign.py` no longer copies
  into `~/Applications`.

## 0.1.0

First version. Format v1, runtime ABI 1.

- **Package format**: `.panpak` file (`.pan` accepted as an alias; a file is
  identified by its magic and signature, never by its extension) with a static
  executable stub, deduplicated zstd chunks, a signed index, a signed manifest
  and an 80-byte footer. Specification in `PANPAK-FORMAT.md`.
- **Verification before execution**: Ed25519 signature over manifest and root
  hash, BLAKE3 hash of the stub bound to the signature, per-chunk BLAKE3
  check before writing. Typed `PANPAK-Exxxx` error codes.
- **Sandbox**: Landlock confinement with no silent fallback, read-only
  trees, private SQLite temporary directory, optional network and device
  allowlists.
- **Trust model**: key shown at install and pinned (TOFU), signed key
  rotation, fail-closed ABI check of the host libraries.
- **CLI** (`panpak`): `keygen`, `pack`, `convert` (AppImage), `install`,
  `install-runtime`, `update`, `rollback`, `open`, `doctor`, `licenses`,
  `release`, `dump-index`, `dump-manifest`.
- **Updates**: incremental updates over HTTPS with range requests, reusing
  the chunks already present.
- **Desktop integration**: launchers and `.desktop` entries, the MIME type
  `application/x-panpak` for the packages (`panpak desktop-integration
  install|remove`); explicit file open for double click.
- **Quality**: conformance suite with an independent Python verifier, fuzz
  targets for every parser (corpus seeds generated by `fuzz/gen-seeds.py`),
  reproducible builds (`scripts/repro-build.sh`, `Dockerfile.repro`),
  SPDX headers, cargo-deny and gitleaks in CI.
